## 1. 结论速览

1. **定时任务不能「转让」，只能在新会话里按登记表重建一遍**
   - 定时任务是用 CronCreate 在某一个会话里建的，只在那个会话里触发，别的会话看不到也删不掉。
   - 接手的做法是：旧会话删掉自己的 11 个任务，新会话按 `loop_tasks.json` 重建，再把新的任务编号写回登记表。
   - 详见 3.2。
2. **同一时刻只能有一个会话持有这 11 个任务**
   - 两个会话都建了，每个任务会触发两次。大部分任务没有防重机制，Slack 会收到两份报告，本体论抓取会多下载一批。
   - 详见 3.2。
3. **每个任务 7 天后自动消失，靠自愈检查任务每 3 天续一次**
   - 自愈检查发现任务缺失就重建，发现任务建立满 4 天就主动删除重建。
   - 自愈检查自己也在这 11 个任务里，必须一起接手。
   - 详见 4.1。
4. **cron 按本机日本时间（JST）触发，市场任务的目标时刻是北京时间（BJT），中间还有一段每个任务各不相同的触发偏移**
   - 实际触发时刻以 CronList 显示的「next run」为准，不要自己按 cron 推算。
   - 详见 2.4。

## 2. 机制

### 2.1 名词

| 名词 | 含义 |
|---|---|
| 定时任务 | 用 CronCreate 建的周期任务。到点时，harness（运行 Claude Code 的程序本身）把登记的 prompt 当作一条用户消息发进会话 |
| 任务编号 | CronCreate 返回的 8 位编号，例如 `df3c52a6`。删除、核对都靠这个编号 |
| 登记表 | `~/projects/my_scripts/loop_tasks.json`，记录每个任务的 cron、prompt、当前任务编号、建立日期 |
| 自愈检查 | 名为 `loop_checker` 的那个定时任务，负责核对和续期，是 11 个任务之一 |
| 续期 | 在任务过期之前删掉它、按同样的 cron 和 prompt 重建一个，让 7 天的有效期从头算 |
| 旧会话 | 目前持有这 11 个任务的会话：工作目录 `~/projects/my_scripts`，会话名 `my-scripts-38` |
| 新会话 | 接手的会话 |

### 2.2 定时任务只活在一个会话里，而且 7 天过期

- **只在建它的会话里触发。** CronList 列出的任务都标着 `[session-only]`。新会话调用 CronList 看不到旧会话的任务，也删不掉。
- **7 天自动过期。** 过期前会最后触发一次，然后消失，不报错。
- **会话退出，任务跟着停。** 会话进程退出后不会再触发。

举个例子：定时任务像贴在某一台电脑上的闹钟。换一台电脑，原来的闹钟带不走，只能在新电脑上照着清单重新设一遍，再把旧电脑上的关掉，否则两台一起响。

### 2.3 登记表 loop_tasks.json

**登记表是这套机制的正本。** 自愈检查、重建、接手，都以这份文件为准。

顶层字段：

| 字段 | 内容 |
|---|---|
| `tasks` | 任务列表，共 11 项 |
| `notify` | Slack 通道说明。`slack_webhook_url` 故意留空，见第 6 章 |
| `_status` | 历次重建、续期、事故的记录，最新的写在最前面 |
| `_timezone_note` | 时区与触发延迟的说明 |
| `_readme` | 一句话说明 |

`tasks` 里每一项的关键字段：

| 字段 | 写入方 | 读取方 | 作用 |
|---|---|---|---|
| `name` | 建任务的人 | 人和自愈检查 | 任务名，全表唯一 |
| `cron` | 建任务的人 | 重建时传给 CronCreate | 按本机 JST 计的 cron 表达式 |
| `prompt` | 建任务的人 | 重建时传给 CronCreate | 到点时发进会话的消息全文 |
| `job_id` | 每次重建后写回 | 自愈检查拿它和 CronList 逐条比对 | 当前任务编号 |
| `created` / `rebuilt` | 首次建立、每次重建后写回 | 自愈检查按它算「满 4 天」 | 日期，格式 `YYYY-MM-DD` |
| `prev_job_id` | 每次重建后写回 | 人 | 上一个任务编号，排查用 |
| `active` | 人 | 人 | 是否启用 |

**写错的后果。** `job_id` 不写回，下一次自愈检查会把这个任务判成「缺失」，再建一个，结果一个任务触发两次。`rebuilt` 不更新，自愈检查会在下一轮又续一次，多一次删除重建，没有其他坏处。

### 2.4 时区与触发偏移

- **本机时钟是日本时间（JST，UTC+9），比北京时间（BJT，UTC+8）快 1 小时。** cron 按 JST 写。
- **harness 给每个任务加了一段触发偏移，各任务不同。** CronList 里「next run」比 cron 写的时刻晚，2026-11-12 的实际值如下：

| 任务 | cron（JST） | CronList 的 next run（JST） | 偏移 | 实际触发（BJT） |
|---|---|---|---|---|
| ontology_digest_daily | 8:00 | 8:30 | +30 分 | 7:30 |
| market_advisor_morning | 9:15 | 9:45 | +30 分 | 8:45 |
| loop_checker | 9:37 | 10:07 | +30 分 | 9:07 |
| sector_morning_0930 | 10:00 | 10:30 | +30 分 | 9:30 |
| daily_ai_news | 10:06 | 10:36 | +30 分 | 9:36 |
| sector_morning_0945 | 10:15 | 10:45 | +30 分 | 9:45 |
| sector_morning_1000 | 10:30 | 11:00 | +30 分 | 10:00 |
| market_advisor_close | 15:15 | 15:45 | +30 分 | 14:45 |
| intraday_daily | 16:00 | 16:03 | +3 分 | 15:03 |
| ycui_sync | 21:00 | 21:30 | +30 分 | 20:30 |
| daily_memory | 23:00 | 23:30 | +30 分 | 22:30 |

- 读法：以 `market_advisor_close` 为例。cron 写 15:15 JST，harness 加 30 分钟，在 15:45 JST 触发，也就是北京时间 14:45，正是尾盘报告的目标时刻。
- **偏移不是固定的 30 分钟。** 建 cron 时，原本都按「固定 +30 分钟」反推，`intraday_daily` 实际只偏移了 3 分钟，所以 11-10、11-11、11-12 连续三天在北京时间 15:01 触发，早于脚本要求的 15:05（见第 5 章 intraday_daily 一行）。
- **重建任务后要重新看 CronList 的 next run。** 偏移可能随重建变化，以 CronList 为准。

## 3. 接手步骤

### 3.1 接手会话的运行条件

| 条件 | 原因 |
|---|---|
| 工作目录 `~/projects/my_scripts` | prompt 里的脚本路径大多写的是绝对路径，但 `daily_ai_news` 等用 `cd ~/projects/my_scripts` 起步；在同一目录下排查最方便 |
| 用 `claude --dangerously-skip-permissions` 启动，或给足权限 | 任务在无人值守时触发，弹出权限确认就会卡住，直到有人点 |
| 环境变量 `SLACK_WEBHOOK_URL` 存在 | `daily_ai_news.py:204` 直接读 `os.environ["SLACK_WEBHOOK_URL"]`。这个变量写在 `~/.zshrc`，从终端启动 claude 时会继承 |
| 会话一直开着，机器不睡眠 | 会话退出或机器睡眠期间，任务不触发 |
| 能调用 Agent 工具 | 本体论精读用 3 个子 agent 并行做 digest |
| 已安装的 skill | `ycui_market_advisor`、`ycui_sync`、`ycui-daily-memory`、`ycui-doc-digest`，都在 `~/.claude/skills/` 下 |

### 3.2 从旧会话搬到新会话

**顺序：先删旧会话的任务，再在新会话里建。** 两边同时持有，任务会重复触发。反过来先建后删，中间可能正好赶上一次触发。

**选一个没有任务触发的时段。** 按 2.4 的表，工作日 JST 11:30 到 15:00 之间、17:00 到 21:00 之间都没有任务触发。

步骤：

1. **在旧会话里删除 11 个任务。** 旧会话 `my-scripts-38` 只听崔扬的指令，新会话不能替它删。请崔扬在旧会话里说「删除全部 11 个定时任务」，旧会话逐个调用 CronDelete，然后用 CronList 确认列表为空。
2. **在新会话里读登记表。** 读 `~/projects/my_scripts/loop_tasks.json` 的 `tasks`，只取 `active` 为 true 的项（当前 11 项都是）。
3. **逐个重建。** 对每一项调用 CronCreate，cron 和 prompt 原样传入，一个字都不改。prompt 里有不少约束是踩坑后加的，改动措辞可能丢掉其中一条。
4. **写回登记表。** 每一项：把原来的 `job_id` 移到 `prev_job_id`，填入新编号，`rebuilt` 改成当天日期。在 `_status` 最前面加一条记录：日期时间、原因（会话交接）、重建的任务清单。
5. **核对。** 调用 CronList，确认 11 条都在，编号和登记表逐条一致。

举个例子：2026-11-10 自愈检查续期时，`market_advisor_morning` 的编号从 `8b908835` 变成 `df3c52a6`，登记表里这一项的 `prev_job_id` 是 `8b908835`，`job_id` 是 `df3c52a6`，`rebuilt` 是 `2026-11-10`。

### 3.3 接手后的验证

- 检查第一次触发的任务是否正常跑完。最近的一个通常是 `ycui_sync`（JST 21:30）或 `daily_memory`（JST 23:30）。
- 第二天早上确认早盘报告（JST 9:45）和三档板块播报都已发到 Slack。

## 4. 日常维护

### 4.1 续期

- **自愈检查的 cron 是 `37 9 */3 * *`**，意思是每月 1、4、7、10、13、16、19、22、25、28、31 号的 9:37 JST，加偏移后约 10:07 JST 触发。
- **它按两条判据处理：**
  - 判据一：登记表里有、CronList 里没有的任务，原样重建。
  - 判据二：`created` 或 `rebuilt` 距今满 4 天的任务，即使还在，也删掉重建。自愈检查自己也适用。
- **满 4 天就续的原因。** 任务 7 天过期，自愈检查 3 天才跑一次。如果只补缺失的，最后一轮检查总落在过期前 3 天之内，那一轮看到一切正常，之后任务集体消失。
- **月末的检查间隔只会变短。** 例如 31 号之后下一次是 1 号，只隔 1 天；所有月份里两次检查的间隔都不超过 3 天。
- **当前状态（2026-11-12）。** 11 个任务都在 2026-11-10 重建，名义上 2026-11-17 过期。11-13 那次检查只满 3 天，不续；11-16 那次满 6 天，全部续期。

举个例子：一个任务 11-10 重建。11-13 检查时 3 天，不动。11-16 检查时 6 天，删掉重建，`rebuilt` 改成 11-16，过期日推到 11-23。如果 11-16 那次检查没跑成（会话不在、机器关机），任务会在 11-17 全部消失。

### 4.2 会话或机器重启之后

- **2026-11-12 机器重启过一次。** 约 18:35 JST 重启，旧会话 19:26 JST 恢复。恢复后 CronList 仍列出 11 个任务，编号不变。
- **恢复后的任务能否照常触发，没有验证过。** 2026-10-12 的同类情况，崔扬要求全部删除重建。所以重启之后，第一件事是看 CronList，再看下一个任务是否按时触发；不触发就按 3.2 第 3 到 5 步重建。
- **重启会清空 `/private/tmp`。** 市场报告的防重标记文件放在这里（见第 5 章），重启当天的标记会丢失。

### 4.3 改任务

- **改 cron、改 prompt、加任务、停任务，都要先经崔扬确认。**
- 确认后的顺序：先改登记表，再删旧任务、按新 cron 和 prompt 重建，最后写回编号。
- 只改了 CronCreate、没改登记表，下一次续期会按登记表把旧版本建回来。

## 5. 各任务的执行要点

**下表每一行是长期有效的执行要点。** 任务的 prompt 已经写了主要要求，这里补的是 prompt 里没写、但实际执行中反复用到的做法。

| 任务 | 内容 | 防重 | 执行要点与已知坑 |
|---|---|---|---|
| ontology_digest_daily | 抓本体论相关论文，做中文 digest PDF | 无 | 先补欠账（脚本开头列出的天数）。每天做 3 篇，派 3 个子 agent 并行，各用独立临时目录 `digest_a`、`digest_b`、`digest_c`，因为 skill 默认的 `/tmp/doc_digest.md` 是固定路径，并行会互相覆盖。做之前先读摘要判断是否对题（主题是本体、知识图谱、知识抽取），标题里有 ontology、taxonomy 不代表对题。产物用 pypdf 重数页数和字符数。只看欠账不要重跑抓取脚本，每跑一次都会下载新文章。截至 11-12，09-23 到 09-29 已清完，下一个是 09-30 |
| market_advisor_morning | 早盘报告，发 Slack | 标记文件 `/private/tmp/claude-502/morning_MMDD.txt` | 执行前看标记文件，存在就只在对话里说明重复触发。KOSPI 只用新浪 `znb_KOSPI` 的第 [3] 个字段，`morning_open_forecast.py` 里的 KOSPI 来自 Yahoo，经常读错，最近一次 11-12 读成 +3.08%，实际 +0.62%。纳指期货 `hf_NQ` 用第 [7] 个字段（前结算价）算涨跌。收盘后纳指期货变动超过 ±0.5% 时，按脚本自己的规则以期货方向为准 |
| market_advisor_close | 尾盘报告，发 Slack，2900 字符以内 | 标记文件 `close_MMDD.txt` | 持仓和关注标的以 `~/.claude/skills/ycui_market_advisor/SKILL.md` 为准，共 5 只。持仓当天涨跌超过 ±4% 且查不到公司层面原因，建议降一档；原因清楚且是板块性的，目前不降，这条理解还等崔扬确认 |
| sector_morning_0930 / 0945 / 1000 | 脚本自己抓板块并发 Slack | 无 | 只运行脚本、贴输出。脚本打印「跳过：……」是开盘初期成交额不够，属正常，不要重试，也不要自己再发一遍 |
| daily_ai_news | 脚本抓 RSS、调模型选 20 条、自己发 Slack | 无 | 报告候选条数、输出条数、`[WARN] Failed to parse` 的源。Simon Willison 的源经常超时，不影响结果 |
| intraday_daily | 采集 30 分钟 K 线，再重算基准 | 无 | 实际在 15:01 BJT 左右触发，早于脚本要求的 15:05，第一步会打印「跳过未收盘的日期」。做法：后台等到 15:06 BJT（用 `until` 循环判断 `TZ=Asia/Shanghai date +%H%M`，不要连续 `sleep`），先把 `intraday_baseline.json` 复制一份备份，再把两步各跑一遍。备份的原因：这个文件不进 git，取数全部失败时重算会写出空基准覆盖它，11-10 发生过一次。抽查手册第 115 行时，读 `intraday_baseline.json` 的 `table_a["下跌"]["6~8%"]`，`down` 里的 `"1"`、`"2"`、`"3"`、`"5"` 和 `up` 里的 `"3"`、`"5"` 就是那六列 |
| ycui_sync | 备份 Claude 会话，同步 my_data、my_scripts | 无 | Claude 备份脚本目前推不上去：旧会话的会话记录文件超过 GitHub 100MB 的单文件上限。每天 18:00 另有一个备份在跑，sync 时只读它的日志，不重跑。my_scripts 里有 4 个代码文件改了但没经崔扬确认，不能用 `git add -A`：只加数据文件（`stock_watch.json`、`loop_tasks.json`），拉取前用 `git stash` 暂存代码改动，推送后再还原。拉取出现冲突就停下来报告，不强推 |
| daily_memory | 汇总当天所有会话，写 `~/projects/my_data/memory/YYYY-MM-DD.md` | 无 | 只 `git add memory/`。写完用关键词扫一遍，确认没有 cookie、token、密码、带 `sk=` 的分享链接、明文密钥 |
| loop_checker | 核对和续期 | 无 | 见 4.1。续期后在 `_status` 最前面记一条 |

**防重标记文件的做法。** 早盘和尾盘报告发完 Slack 后，把报告正文写到 `/private/tmp/claude-502/morning_MMDD.txt` 或 `close_MMDD.txt`。下次触发先看文件在不在。这个目录在机器重启时会被清空，见 4.2。

## 6. 红线

- **密钥不写进 my_scripts。** my_scripts 是公开仓库，Slack 会扫描公开仓库里的 webhook 并吊销。
  - Slack webhook：环境变量 `SLACK_WEBHOOK_URL`，没有就读本地文件 `~/.slack_webhook_url`。板块播报脚本读 `~/.config/ycui/slack.json`。
  - AI 晨报用的模型凭据：环境变量 `LLM_API_KEY`，没有就读 `~/projects/umu/csrs/.env`。
  - `loop_tasks.json` 里的 `slack_webhook_url` 必须保持为空。
- **没经崔扬确认，不改代码、不改配置、不提交代码。**
- **不往 memory 文件和任何仓库里写凭据。**
- **所有输出用中文，按 `~/.claude/output-styles/jiang-ming-bai.md` 的写法。**
- **微信通道已经失效，不要尝试。**
