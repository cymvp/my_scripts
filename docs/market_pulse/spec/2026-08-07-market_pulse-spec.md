# market_pulse 盘中涨跌速度监控 — 设计文档

- 日期：2026-08-07
- 模块：market_pulse
- 状态：设计确认，待拆任务

## 1. 要解决的问题

盘中看到自己的股票在跌，需要立刻分清两种情况：只有这只票在跌（个股层面出事），还是整个市场都在跌（系统性回撤）。这两种情况的应对完全不同，但从单只票的行情上看不出区别。

现有工具都答不了这个问题：`stock_watch.py` 只显示自选股各自的涨跌幅，没有横向对照；`sector_trend.py` 是多日趋势，粒度是天；`intraday_guide.py` 的统计基准是历史概率，不是实时状态。

本模块补上实时横向对照这一块。**它只描述已经发生的事，不做任何方向预测。**

## 2. 三类指标

### 2.1 速度

**含义：** 最近 w 秒内，涨跌幅变化了多少个百分点。

**公式：**

```
r(t)  = (现价(t) − 昨收) ÷ 昨收 × 100          单位 %
v(w)  = r(t) − r(t − w)                        单位 百分点(pp)
```

**为什么用涨跌幅之差而不是价格变化率：** 池子里有 977 元的中际旭创，也有 38 元的国际复材。价格变化率会让不同价位的票不可比，涨跌幅之差可以直接放进同一张表。代价是它对高价股和低价股的敏感度不同，这一点已与用户确认接受。

**算例：** 中际旭创昨收 955.00。13:24:00 价 979.00，`r = (979.00 − 955.00) ÷ 955.00 × 100 = +2.51%`；13:24:15 价 977.00，`r = +2.30%`。`v(15秒) = 2.30 − 2.51 = −0.21 pp`，读作「最近 15 秒涨跌幅掉了 0.21 个百分点」。

**三个窗口：** w = 15 秒、60 秒、300 秒。三个一起看能分出「刚开始跌」和「跌了一阵快止住了」——短窗比长窗快说明在加速，短窗比长窗慢说明在减速。

### 2.2 聚合速度

**含义：** 一组票的整体速度。

**公式：** `V(w) = median{ v_i(w) : i ∈ 该组，且 v_i(w) 不为 None }`

**为什么用中位数不用平均数：** 池子里有涨停跌停的极端票。2026-08-07 11:30 的实测数据里，PCB/覆铜板赛道中位 +7.62%，MLCC 只有 +0.39%，平均数会被少数暴涨票拉偏。

**分组层次：** 单只票、所属赛道（`intraday_guide.SECTOR` 的 14 个细分赛道）、38 只科技池、大盘指数（创业板指、上证、科创 50）。

### 2.3 宽度

**含义：** 此刻池子里多少只在涨、多少只在跌；以及最近 w 秒里有多少只从涨转跌或反过来。

**公式：**

```
上涨家数 = 满足 r_i(t) > 0 的票数
下跌家数 = 满足 r_i(t) < 0 的票数
平盘家数 = 满足 r_i(t) = 0 的票数
翻向数   = 满足 sign(r_i(t)) ≠ sign(r_i(t − w)) 且两者都不为 0 的票数
```

**算例（2026-08-07 11:30 实测）：** 38 只票里上涨 34 只、下跌 4 只、平盘 0 只。

### 2.4 超额

**含义：** 你的票的涨跌幅减去基准的涨跌幅，回答跑赢还是跑输。

**公式：** `excess = r_个股(t) − r_基准(t)`，单位百分点

**算例（2026-08-07 11:30 实测）：** 中际旭创 +2.35%，科技池中位数 +1.66%，`excess = 2.35 − 1.66 = +0.69 pp`。国际复材 +7.24%，`excess = +5.58 pp`。

### 2.5 池内排名

**含义：** 你的票的涨跌幅在池内排第几。超额单独看没有信息量，配上排名才知道是强是弱。

**公式：** `排名 = (涨跌幅严格大于你的票数) + 1`。并列时给相同名次，之后的名次跳号——三只票涨跌幅为 [5.0, 3.0, 3.0, 1.0] 时名次是 1、2、2、4。分母是**有效票数**，不是固定的 38。

**算例（2026-08-07 11:30 实测）：** 中际旭创 +2.35% 排 17/38（前 45%）；国际复材 +7.24% 排 4/38（前 11%）。

### 2.6 判定

回答「是我独跌还是大家都跌」。**只用计数和排序，不依赖任何需要标定的阈值。**

| 条件 | 判定 |
|---|---|
| 池内上涨占比 ≥ 60% 且 个股 r < 0 | 独跌 |
| 池内下跌占比 ≥ 60% 且 个股 r < 0 | 同跌 |
| 池内上涨占比 ≥ 60% 且 个股 r > 0 | 同涨 |
| 其余 | 分化 |

**占比的分母是有效票数，不是固定的 38。** 38 只全部有效时，60% 对应 22.8 只，所以 ≥23 只命中；若只有 35 只有效，60% 对应 21 只。比例按闭区间取，正好等于 60% 算命中。

个股 r 正好为 0（平盘）时一律判「分化」，不进前三行。

判定后面固定跟一句参照：「你在池内排 N/M，速度排 K/M」，M 为有效票数。

**为什么不设速度阈值：** 「跌多快才算真的在跌」要用历史分布标定，而 15 秒粒度的历史目前一条都没有，本模块的采集正是这批数据的起点。在积累足够样本之前，面板上不出现任何未经标定的快慢定性词。等 `pulse_store.jsonl` 攒够数据，再回头补分位参照。

## 3. 架构

```
market_pulse.py                      新建
  纯函数区（单测覆盖 100%）
    speed(r_now, r_past)             算速度
    aggregate(values)                中位数聚合，返回 (中位数, 有效数)
    breadth(rs_now, rs_past)         算宽度
    excess(r_stock, r_bench)         算超额
    rank(r_stock, all_rs)            算池内排名
    verdict(breadth, r_stock)        出判定
    pick_snapshot(store, target, tol) 按容差取历史快照
    in_session(hhmm)                 交易时段判断
    merge_codes(watch, pool, idx)    合并去重代码列表
    split_result(quotes, watch, pool) 分拣返回结果
    render_panel(state)              命令行完整面板文本
    render_strip(state)              悬浮窗单行文案
  IO 区（集成测试打真实接口）
    append_store(snapshot)           快照追加落盘
    load_store(seconds)              读回最近 N 秒的快照
    rotate_store()                   跨日清空

pulse_store.jsonl                    新建，与 intraday_bars.jsonl 同目录同风格

stock_watch.py                       改动约 30 行
```

**取数完全并入 `stock_watch.py` 现有的 `fetch_quotes()`。** 该函数按市场分三路，A 股全部走一个新浪批量请求（`stock_watch.py:220-243`）。38 只池子票和 3 个指数都是 A 股，直接并进那一路。

**实测（2026-08-07）：** 自选 10 个 A 股代码 + 池子 38 + 指数 3，去重后 45 个，URL 长度 430 字符，5 次请求全部 45/45 返回，耗时中位 421 毫秒。**本模块产生 0 个额外网络请求。**

**采样间隔跟随悬浮窗现有的 3 秒刷新**，不另设定时器。新浪 L1 本身是 3 秒快照，采得更快拿不到新数据。15 秒窗口因此有 5 个采样点。

**为什么两个前端而不是全塞进悬浮窗：** 悬浮窗是一条横向窄条，放不下完整面板。计算与显示分离之后，核心逻辑是纯函数可以完整单测，命令行入口还能被 `ycui_market_advisor` 这个 skill 和 loop 任务直接调用。

## 4. 数据流

### 4.1 交易时段

只在 9:30–11:30 和 13:00–15:00 采样。

集合竞价（9:15–9:25）不采——那时的价格是虚拟撮合价，与连续竞价不是同一个东西，混进速度序列会产生假信号。午休和盘后不采，避免文件里灌入重复快照。

### 4.2 落盘格式

```json
{"t":"2026-08-07 13:24:15","q":{"sz300308":977.45,"sz300502":447.0},"idx":{"sz399006":3578.24,"sh000001":3915.89,"sh000688":1734.42}}
```

每行一条。**每天首次写入前检查最后一条的日期，不是今天就清空重建。** 昨天的价格接到今天的序列上会算出跨夜跳空的假速度。

体积估算：每条约 500 字节 × 4800 条（4 小时 ÷ 3 秒）≈ **每天 2.4 MB**，当天用完即弃，不保留历史。

### 4.3 窗口取值

算 `v(w)` 需要 `t − w` 时刻的价格，采样点不会正好落在该时刻上。**取时间戳距离 `t − w` 最近、且偏差不超过 `w ÷ 3` 的那条快照。** 偏差超限则该窗口不可用。

**举例：** 现在 13:24:15，算 15 秒窗口需要 13:24:00 的快照，允许偏差 5 秒，所以 13:23:55 至 13:24:05 之间的快照都能用。

### 4.4 三种不可用状态

| 状态 | 面板显示 | 触发条件 |
|---|---|---|
| 采集未运行 | `不可用（悬浮窗未启动）` | 文件为空，或最后一条距现在超过 60 秒 |
| 数据不足 | `不可用（已采集 47 秒，需 300 秒）` | 文件里最早一条距现在不足 w |
| 窗口无快照 | `不可用（该窗口无快照）` | 4.3 的偏差超限 |

**三种都不给数字，也不用别的窗口或别的数据源的数去凑。** 这条按用户 CLAUDE.md 的「计算类代码不允许 fallback 默默牺牲正确性」执行。三个窗口全部只用自采数据，不引入腾讯分时等 1 分钟粒度的接口。

## 5. 错误处理

| 情况 | 处理 |
|---|---|
| 新浪接口超时或返回空 | 跳过这次采样，不写空快照；悬浮窗保留上次文案并加 `·` 标记数据陈旧；连续失败 5 次（15 秒）在面板顶部报「行情中断」 |
| 某只票停牌或昨收为 0 | 直接剔除，不列名、不提示 |
| 池内有效票少于 20 只 | 池子层面指标全部标「样本不足（仅 N 只有效）」，不出判定 |
| 落盘文件某行不是合法 JSON | 跳过该行继续读，面板底部报「跳过 N 行损坏记录」 |
| 磁盘写失败 | 悬浮窗照常显示当前快照，速度全部标不可用；每 60 秒重试 |

**有效票门槛为什么是 20：** 判定的算法是数人头，结论成立的前提是数据基本齐全。如果只有 18 只返回而其中 12 只在涨，算出 67% 照样会打印「同涨」，但另外 20 只的涨跌完全未知。更麻烦的是不知道缺的是哪些——若丢的恰好是 12 只科创板票，剩下的池子就缺了半导体设备和晶圆制造，结论会系统性偏向剩余赛道。这是方向性错误，不是精度问题。

合并请求之后 45 个代码走同一个请求，要么全部返回要么整体失败，所以这条平时不会触发，只在极端行情大面积停牌时起作用。保留成本是几行代码。

**贯穿原则：任何一次降级都在界面上留痕，不存在「看起来正常但底下是估算值」的情况。**

## 8. 明确不做的事

- **不做方向预测。** 只描述已经发生的涨跌，不推断接下来会怎么走。
- **不给「跌得快/慢」的定性词。** 在 15 秒粒度的历史分布标定出来之前，只给计数、排名和原始数值。
- **不做告警推送。** 阈值定不好会变成骚扰，等面板用一阵子有了手感再议。
- **不保留历史快照。** `pulse_store.jsonl` 当天用完即弃。若日后要做分位标定，再单独设计归档方案。
- **不改动 `stock_watch.py` 的自选逻辑。** 只在 `refresh()` 里并入池子代码、在横条末尾加一个格子。
